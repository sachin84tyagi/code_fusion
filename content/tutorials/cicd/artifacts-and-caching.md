# Artifacts

**Artifacts** are files generated by a pipeline job that you want to keep.

```
Use cases:
  → Built application (dist/)
  → Test reports (junit.xml)
  → Coverage reports (coverage/)
  → JAR files (target/app.jar)
  → Docker image tarballs
  → Log files
```

---

# Upload Artifact

```yaml
steps:
  - name: Build
    run: npm run build

  - name: Upload dist folder
    uses: actions/upload-artifact@v4
    with:
      name: build-output         # Artifact name
      path: dist/                # What to save
      retention-days: 7          # Keep for 7 days (default 90)
```

---

# Download Artifact

```yaml
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with:
          name: build-output
          path: dist/

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - uses: actions/download-artifact@v4
        with:
          name: build-output

      - run: ls -la   # dist/ folder is now available
      - run: ./deploy.sh dist/
```

---

# Upload Multiple Artifacts

```yaml
steps:
  - name: Run tests
    run: npm test -- --coverage

  - name: Upload test results
    uses: actions/upload-artifact@v4
    with:
      name: test-results
      path: |
        coverage/
        test-results.xml
      if-no-files-found: warn    # warn / error / ignore
```

# Caching

**Cache** saves files between pipeline runs to avoid re-downloading or re-building.

```
Without cache:
  Run 1: npm install (download 500 packages) → 3 minutes
  Run 2: npm install (download 500 packages again) → 3 minutes
  Run 3: npm install (download 500 packages again) → 3 minutes

With cache:
  Run 1: npm install (download 500 packages) → 3 minutes
  Run 2: Cache hit! Restore packages → 15 seconds
  Run 3: Cache hit! Restore packages → 15 seconds
```

---

# Cache Action

```yaml
- name: Cache node_modules
  uses: actions/cache@v4
  with:
    path: node_modules           # What to cache
    key: ${{ runner.os }}-node-${{ hashFiles('package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-node-
```

**How it works:**

```
1. GitHub computes the key
2. If cache with that key exists → restore (CACHE HIT)
3. Run npm install (much faster, packages already there)
4. If key differs → download fresh (CACHE MISS)
5. After job → save new cache with the key
```

---

# Cache Keys

The cache key determines when to use the cache vs download fresh.

```yaml
# Node.js — invalidate when package-lock.json changes
key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}

# Python — invalidate when requirements.txt changes
key: ${{ runner.os }}-pip-${{ hashFiles('**/requirements.txt') }}

# Java Maven — invalidate when pom.xml changes
key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}

# Java Gradle — invalidate when build.gradle changes
key: ${{ runner.os }}-gradle-${{ hashFiles('**/*.gradle*') }}

# Go — invalidate when go.sum changes
key: ${{ runner.os }}-go-${{ hashFiles('**/go.sum') }}
```

`hashFiles()` generates a hash of the file content.

If `package-lock.json` changes → different hash → fresh cache.

---

# Restore Keys (Fallback)

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('**/package-lock.json') }}
    restore-keys: |
      ${{ runner.os }}-npm-     # Fallback: any npm cache for this OS
      ${{ runner.os }}-         # Fallback: any cache for this OS
```

If exact key not found → try restore-keys in order.

Partial cache hit is better than no cache.

# Built-in Cache Support

Many setup actions have built-in caching:

```yaml
# Node.js with built-in cache
- uses: actions/setup-node@v4
  with:
    node-version: '18'
    cache: 'npm'          # ← built-in caching!

# Python with built-in cache
- uses: actions/setup-python@v5
  with:
    python-version: '3.11'
    cache: 'pip'          # ← built-in caching!

# Java with built-in cache
- uses: actions/setup-java@v4
  with:
    java-version: '17'
    distribution: 'temurin'
    cache: 'maven'        # ← built-in caching!
```

Simplest way to cache. Recommended.

# Complete Node.js Example with Cache

```yaml
name: Node.js CI with Cache

on: push

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Setup Node with cache
        uses: actions/setup-node@v4
        with:
          node-version: '18'
          cache: 'npm'            # Cache node_modules automatically

      - name: Install dependencies
        run: npm ci               # Uses cached packages if available

      - name: Run tests
        run: npm test

      - name: Build
        run: npm run build

      - name: Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: production-build
          path: dist/
          retention-days: 30
```

# Cache vs Artifact

| | Cache | Artifact |
| --- | --- | --- |
| Purpose | Speed up future runs | Save outputs for use/download |
| Persists across | Runs (same branch) | Jobs in same run |
| Size limit | 10 GB | 500 MB (free), 2 GB (enterprise) |
| Auto-expires | 7 days of no access | 90 days (configurable) |
| Best for | node_modules, pip, Maven | dist/, JARs, test reports |

# Company Example — Swiggy

Swiggy's pipeline reduced from 18 min to 4 min using caching:

```yaml
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # Cache Maven dependencies → saves 8 minutes
      - uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: 'temurin'
          cache: 'maven'

      # Cache node_modules → saves 3 minutes
      - uses: actions/setup-node@v4
        with:
          node-version: '18'
          cache: 'npm'

      - run: mvn test
      - run: npm test

      # Save test reports
      - uses: actions/upload-artifact@v4
        with:
          name: test-reports
          path: |
            target/surefire-reports/
            coverage/
```

Pipeline went from 18 minutes → 4 minutes.

# Interview Questions

## Q1. What is a GitHub Actions artifact?

**Best Answer**

> An artifact is a file or directory generated by a pipeline job that is saved for later use. Use `actions/upload-artifact` to save it and `actions/download-artifact` to retrieve it in another job. Common artifacts are build output (dist/), test reports, coverage reports, and JAR files.

---

## Q2. What is caching in CI/CD and why is it important?

Caching stores files (like node_modules, Maven dependencies) between pipeline runs. If the dependencies haven't changed, the cache is restored instead of downloading again. This reduces pipeline time from minutes to seconds for dependency installation.

---

## Q3. What is a cache key?

A cache key is a unique string that identifies a specific cache entry. It typically includes the OS and a hash of the dependency file (package-lock.json, pom.xml). If the key changes (because the file changed), the cache is invalidated and dependencies are re-downloaded.

---

## Q4. What is the difference between a cache and an artifact?

A cache persists dependency files across multiple pipeline runs to speed up future runs. An artifact saves build outputs (generated files) for use within the same run or for download after the run. Cache is for performance; artifacts are for sharing build outputs.
